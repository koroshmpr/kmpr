بیشتر مشکلاتی که در پروژه‌های Next.js دیده‌ام، از جنس «چرا این صفحه به‌روز نمی‌شود؟» یا برعکس «چرا این صفحه این‌قدر کند است؟» بوده‌اند. هر دو یک ریشه دارند: تصمیم نگرفتن درباره اینکه صفحه کی ساخته شود و داده‌اش چقدر کش شود. در این درس رندرینگ در Next.js را از زاویه همین تصمیم‌ها توضیح می‌دهم: Server Component و Client Component، صفحه ثابت و پویا، ISR و revalidate.

این درس سوم دوره آموزش Next.js برای کسب‌وکار است و بعد از درس App Router می‌آید.

Server Component: پیش‌فرضی که باید نگهش دارید

در App Router هر کامپوننتی که 'use client' نداشته باشد، Server Component است. یعنی:

  • روی سرور اجرا می‌شود و می‌تواند async باشد و مستقیم داده بخواند.
  • کد آن به مرورگر فرستاده نمی‌شود؛ کتابخانه‌های سنگین (مثلاً برای تبدیل Markdown یا فرمت تاریخ) حجم جاوااسکریپت سایت را بالا نمی‌برند.
  • به رازها (کلید API، رمز دیتابیس) دسترسی دارد، چون هیچ‌وقت در مرورگر اجرا نمی‌شود.
  • نمی‌تواند state، رویداد کلیک یا هوک‌هایی مثل useEffect داشته باشد.

Client Component: جزیره‌های تعاملی

'use client' مرز را مشخص می‌کند: آن فایل و هر چیزی که import می‌کند در مرورگر هم اجرا می‌شود. سه قاعده که رعایتشان حجم سایت را پایین نگه می‌دارد:

  1. مرز را تا جای ممکن پایین ببرید. به‌جای Client کردن کل صفحه به‌خاطر یک دکمه، فقط همان دکمه را Client Component کنید.
  2. داده را از سرور به‌عنوان props پاس بدهید. Client Component لازم نیست داده اولیه را خودش با useEffect بگیرد؛ این کار یک رفت‌وبرگشت اضافه و یک صفحه خالی اولیه می‌سازد.
  3. props باید قابل سریال شدن باشند. رشته، عدد، آرایه و آبجکت ساده مشکلی ندارند؛ تابع معمولی را نمی‌شود از سرور به کلاینت پاس داد.

یک نکته که خیلی‌ها را گیج می‌کند: Client Component هم در اولین بارگذاری روی سرور به HTML تبدیل می‌شود و بعد در مرورگر «زنده» (hydrate) می‌شود. «Client» یعنی کدش به مرورگر هم می‌رود، نه اینکه فقط در مرورگر رندر شود.

صفحه ثابت یا پویا؟

Next.js هنگام build برای هر مسیر تصمیم می‌گیرد آن را از قبل بسازد یا برای هر درخواست. اگر صفحه از چیزی وابسته به درخواست استفاده کند، مثل cookies()، headers() یا searchParams، پویا می‌شود. در غیر این صورت می‌تواند ثابت باشد. خروجی دستور next build نوع هر مسیر را نشان می‌دهد؛ عادت کنید بعد از هر تغییر مهم آن را نگاه کنید. صفحه‌ای که انتظار دارید ثابت باشد ولی پویا شده، معمولاً یعنی جایی ناخواسته کوکی یا هدر خوانده شده است.

کش داده: fetch و revalidate

در نسخه‌های جدید Next.js (از ۱۵ به بعد) fetch به‌طور پیش‌فرض کش نمی‌شود و باید صریح بگویید هر داده چقدر معتبر است. این تغییر نسبت به نسخه ۱۴ است و مثال‌های قدیمی اینترنت را گمراه‌کننده می‌کند:

// هر ۶۰ ثانیه حداکثر یک بار از منبع خوانده می‌شود
const res = await fetch('https://api.example.com/prices', {
  next: { revalidate: 60, tags: ['prices'] },
});

// همیشه تازه؛ برای داده‌ای که به کاربر وابسته است
const me = await fetch('https://api.example.com/me', { cache: 'no-store' });

برای تنظیم کل صفحه هم می‌توانید در فایل صفحه بنویسید export const revalidate = 300;. انتخاب عدد یک تصمیم کسب‌وکاری است، نه فنی؛ از خودتان بپرسید «کاربر اگر داده‌ای ببیند که N ثانیه قدیمی است، مشکلی پیش می‌آید؟»

ISR و بازسازی با رویداد

ISR یعنی صفحه ثابت می‌ماند و سریع سرو می‌شود، ولی بعد از گذشت زمان revalidate، اولین درخواست بعدی نسخه قدیمی را می‌گیرد و هم‌زمان نسخه جدید در پس‌زمینه ساخته می‌شود. این الگو برای وبلاگ و فروشگاه ایده‌آل است.

بهتر از انتظار برای زمان، بازسازی با رویداد است. وقتی مقاله‌ای در CMS ذخیره شد، CMS یک وب‌هوک به سایت Next.js می‌فرستد و همان صفحه بلافاصله بازسازی می‌شود:

// app/api/revalidate/route.ts
import { revalidatePath, revalidateTag } from 'next/cache';

export async function POST(req: Request) {
  if (req.headers.get('x-secret') !== process.env.REVALIDATE_SECRET) {
    return new Response('forbidden', { status: 403 });
  }
  const { slug } = await req.json();
  revalidatePath(`/blog/${slug}`);
  revalidateTag('posts');
  return Response.json({ revalidated: true });
}

در وردپرس هدلس، این وب‌هوک روی هوک save_post فرستاده می‌شود؛ جزئیاتش در راهنمای وردپرس هدلس با Next.js آمده است. حتماً مسیر را با یک راز محافظت کنید، وگرنه هر کسی می‌تواند با درخواست‌های پشت‌سرهم سرور شما را مشغول بازسازی کند.

اشتباه‌های رایج کش

  • کش کردن داده کاربر در کش مشترک: اگر پاسخی که به کوکی کاربر وابسته است کش شود، ممکن است کاربر دیگری آن را ببیند. داده شخصی همیشه no-store.
  • Client کردن کل صفحه برای یک تایمر: نتیجه‌اش جاوااسکریپت سنگین و صفحه‌ای است که موتور جست‌وجو ممکن است خالی ببیند.
  • revalidate صفر برای همه‌چیز «برای اطمینان»: هر بازدید به API بیرونی می‌رسد و با ترافیک بالا هم سرور کند می‌شود و هم به سقف درخواست API می‌خورید.
  • تست نکردن build تولید: رفتار کش در next dev با next build و next start فرق دارد. قبل از دیپلوی، نسخه تولید را محلی اجرا کنید.

جمع‌بندی

رندرینگ در Next.js با سه سؤال تعیین می‌شود: این کامپوننت به تعامل در مرورگر نیاز دارد؟ این صفحه به درخواست کاربر وابسته است؟ این داده چقدر می‌تواند قدیمی باشد؟ جواب درست به این سه، هم سایت را سریع می‌کند و هم هزینه سرور و API را پایین نگه می‌دارد.

درس بعد، اتصال Next.js به API و داده زنده، همین مفاهیم را روی یک داشبورد قیمت زنده پیاده می‌کند. درس قبل App Router بود و نقشه کامل دوره در راهنمای Next.js است.

اگر سایت Next.js دارید که کند است یا داده‌هایش درست به‌روز نمی‌شوند، فرم درخواست پروژه را پر کنید تا بررسی‌اش کنیم.
