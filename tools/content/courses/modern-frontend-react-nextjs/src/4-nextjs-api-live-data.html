سایتی که قیمت طلا، سکه یا ارز نشان می‌دهد، فقط وقتی ارزش دارد که قیمت‌هایش درست و تازه باشند. در کار روی این سایت‌ها سه مشکل را بارها دیدم: صفحه‌ای که با هر بازدید API بیرونی را صدا می‌زد و با بالا رفتن ترافیک خطای ۴۲۹ می‌گرفت، کلید API که در کد سمت مرورگر پیدا می‌شد، و صفحه‌ای که وقتی منبع داده فرمت پاسخش را عوض کرد، کاملاً سفید شد. این درس الگوهایی را نشان می‌دهد که برای اتصال Next.js به API استفاده می‌کنم تا هیچ‌کدام از این‌ها تکرار نشود.

این درس چهارم دوره آموزش Next.js برای کسب‌وکار است و بر پایه مفاهیم درس رندرینگ و کش ساخته شده است.

معماری: مرورگر هرگز مستقیم به API بیرونی وصل نمی‌شود

ساختاری که برای داده بیرونی استفاده می‌کنم سه لایه دارد:

  1. یک ماژول سمت سرور (مثلاً lib/prices.ts) تنها جایی است که API بیرونی را صدا می‌زند. کلید، timeout، کش و اعتبارسنجی همه همین‌جاست.
  2. Server Componentها برای نمایش اولیه صفحه از همین ماژول می‌خوانند.
  3. یک Route Handler (مثلاً /api/prices) همان داده را برای به‌روزرسانی‌های بعدی در مرورگر سرو می‌کند.

نتیجه این است که هزار بازدیدکننده هم‌زمان، به هزار درخواست به API بیرونی تبدیل نمی‌شوند؛ همه از کش سرور شما می‌خوانند و فقط سرور، با نرخ کنترل‌شده، به منبع وصل می‌شود.

کلید API: فقط در متغیر محیطی سرور

در Next.js هر متغیر محیطی که با NEXT_PUBLIC_ شروع شود، داخل کد مرورگر قرار می‌گیرد و هر کسی می‌تواند آن را ببیند. کلید API هرگز نباید این پیشوند را داشته باشد:

# .env.local  (در git کامیت نمی‌شود)
PRICES_API_URL=https://api.example.com/v1
PRICES_API_KEY=xxxxxxxx

# درست نیست: این مقدار در مرورگر دیده می‌شود
# NEXT_PUBLIC_PRICES_API_KEY=xxxxxxxx

برای اطمینان بیشتر، بالای ماژول سمت سرور import 'server-only'; بنویسید. اگر کسی اشتباهی این ماژول را در یک Client Component استفاده کند، build با خطا متوقف می‌شود.

ماژول داده: timeout، کد وضعیت و اعتبارسنجی

هر منبع داده دیر یا زود کند می‌شود، خطا می‌دهد یا فرمت پاسخش را عوض می‌کند. ماژول داده باید هر سه حالت را مدیریت کند:

// lib/prices.ts
import 'server-only';
import { z } from 'zod';

const PriceSchema = z.object({
  symbol: z.string(),
  title: z.string(),
  buy: z.number(),
  sell: z.number(),
  updated_at: z.string(),
});
const ResponseSchema = z.object({ data: z.array(PriceSchema) });
export type Price = z.infer;

export async function getPrices(): Promise {
  const res = await fetch(`${process.env.PRICES_API_URL}/prices`, {
    headers: { Authorization: `Bearer ${process.env.PRICES_API_KEY}` },
    next: { revalidate: 30, tags: ['prices'] },
    signal: AbortSignal.timeout(5000), // بیش از ۵ ثانیه منتظر نمان
  });
  if (!res.ok) throw new Error(`prices api ${res.status}`);
  const parsed = ResponseSchema.safeParse(await res.json());
  if (!parsed.success) {
    console.error('[prices] unexpected format', parsed.error.issues);
    throw new Error('prices api format changed');
  }
  return parsed.data.data;
}

اعتبارسنجی با کتابخانه‌ای مثل zod دو فایده دارد: نوع TypeScript مستقیم از همان طرح ساخته می‌شود و وقتی منبع داده مثلاً sell را به‌صورت رشته یا داخل یک آبجکت تو در تو فرستاد، خطا دقیقاً در لاگ مشخص است، نه به شکل «undefined» در وسط صفحه.

نرخ مجاز درخواست و خطای ۴۲۹

تقریباً همه APIهای قیمت محدودیت تعداد درخواست دارند. اگر از آن بگذرید، پاسخ 429 Too Many Requests می‌گیرید و گاهی تا مدتی کامل مسدود می‌شوید. راه‌حل‌ها به ترتیب اهمیت:

  • کش سمت سرور با عددی که با سقف API جور باشد. اگر API در دقیقه ۶۰ درخواست اجازه می‌دهد و چهار نماد دارید که جدا خوانده می‌شوند، revalidate کمتر از ۴ ثانیه برای هر نماد شما را به سقف می‌رساند.
  • یک درخواست به‌جای چند درخواست. اگر API امکان گرفتن چند نماد در یک درخواست را دارد، از آن استفاده کنید.
  • احترام به هدر Retry-After. وقتی ۴۲۹ گرفتید، تا زمانی که API گفته دوباره درخواست نزنید.
  • تلاش دوباره با فاصله افزایشی (exponential backoff) برای خطاهای موقت مثل ۵۰۲ و ۵۰۳، با سقف تعداد تلاش. برای ۴۰۰ و ۴۰۱ تلاش دوباره فایده‌ای ندارد.

وقتی منبع داده از کار افتاد: آخرین داده سالم

برای کاربر، قیمتی که یک دقیقه قدیمی است و برچسب زمان دارد، خیلی بهتر از صفحه خطاست. الگوی ساده من نگه داشتن آخرین پاسخ سالم و نمایش آن با هشدار است:

let lastGood: { at: number; rows: Price[] } | null = null;

export async function getPricesSafe() {
  try {
    const rows = await getPrices();
    lastGood = { at: Date.now(), rows };
    return { rows, stale: false };
  } catch (e) {
    if (lastGood) return { rows: lastGood.rows, stale: true, at: lastGood.at };
    throw e; // هیچ داده‌ای نداریم؛ error.tsx نمایش داده می‌شود
  }
}

این حافظه فقط در همان پردازش سرور می‌ماند. اگر چند نمونه از سایت اجرا می‌شود یا سرور ری‌استارت می‌شود، آخرین داده سالم را در Redis یا دیتابیس نگه دارید. در رابط کاربری هم وقتی stale برقرار است، زمان آخرین به‌روزرسانی را نشان دهید تا کاربر بداند به چه داده‌ای نگاه می‌کند.

به‌روزرسانی در مرورگر: polling، SSE یا WebSocket

بعد از بارگذاری اولیه، قیمت‌ها باید در صفحه باز هم تازه شوند. سه روش رایج:

روشکی مناسب استهزینه
Polling (درخواست دوره‌ای)به‌روزرسانی هر چند ثانیه کافی استساده‌ترین؛ با کش سرور سبک است
Server-Sent Eventsجریان یک‌طرفه از سرور، تغییرات مکرراتصال باز برای هر کاربر
WebSocketارتباط دوطرفه، مثل چت یا سفارش‌گذاریپیچیده‌تر؛ معمولاً سرویس جدا می‌خواهد

برای بیشتر سایت‌های قیمت، polling با فاصله‌ای برابر revalidate سرور کافی است. نکته مهم این است که وقتی تب در پس‌زمینه است، درخواست نزنید:

'use client';
import { useEffect, useState } from 'react';

export function LivePrices({ initial }: { initial: Price[] }) {
  const [rows, setRows] = useState(initial);
  useEffect(() => {
    const tick = async () => {
      if (document.hidden) return; // تب دیده نمی‌شود؛ درخواست نزن
      const res = await fetch('/api/prices');
      if (res.ok) setRows((await res.json()).rows);
    };
    const id = setInterval(tick, 30_000);
    return () => clearInterval(id);
  }, []);
  return ;
}

داده اولیه از Server Component به‌عنوان initial می‌آید؛ پس صفحه از اول پر است و موتور جست‌وجو هم قیمت‌ها را در HTML می‌بیند.

نمایش عدد و تاریخ برای کاربر فارسی‌زبان

  • برای اعداد از toLocaleString('fa-IR') یا Intl.NumberFormat('fa-IR') استفاده کنید تا ارقام فارسی و جداکننده هزارگان درست باشند.
  • تاریخ را با Intl.DateTimeFormat('fa-IR-u-ca-persian', …) شمسی کنید؛ برای بیشتر نیازها کتابخانه جدا لازم نیست.
  • داده را همیشه به شکل عدد لاتین نگه دارید و فقط هنگام نمایش فارسی کنید. محاسبه روی رشته‌ای با ارقام فارسی، منبع باگ‌های عجیب است.
  • تغییر قیمت را فقط با رنگ نشان ندهید؛ فلش یا علامت مثبت و منفی هم بگذارید تا برای همه کاربران قابل فهم باشد.

پایش: قبل از کاربر بفهمید

یکپارچه‌سازی با API بیرونی بدون پایش، بی‌صدا خراب می‌شود. حداقل‌ها: لاگ با پیشوند مشخص برای هر خطا، هشدار وقتی داده بیش از حد مجاز کهنه شد و یک مسیر سلامت (/api/health) که سرویس مانیتورینگ آن را بررسی کند. روش‌های پایش را در درس مانیتورینگ سایت از دوره امنیت و نگهداری توضیح داده‌ام.

جمع‌بندی

اتصال درست به API یعنی کلید فقط روی سرور، یک ماژول داده با timeout و اعتبارسنجی، کشی که با سقف درخواست API هماهنگ است، آخرین داده سالم برای زمان قطعی و به‌روزرسانی سبک در مرورگر. این الگوها هم برای قیمت‌های بازار کار می‌کنند و هم برای هر داده بیرونی دیگر، از وضعیت سفارش تا موجودی انبار.

درس قبل رندرینگ و کش در Next.js بود. درس بعد، دیپلوی Next.js روی سرور، این پروژه را روی سرور واقعی می‌برد. نقشه کامل دوره در راهنمای Next.js است.

اگر سایتتان باید به API قیمت، درگاه یا CRM وصل شود و این اتصال باید پایدار بماند، فرم درخواست پروژه را پر کنید.
