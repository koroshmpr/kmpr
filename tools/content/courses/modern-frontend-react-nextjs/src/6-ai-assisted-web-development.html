اولین باری که برای یک پروژه واقعی از ChatGPT کد گرفتم، کد کار کرد و همین مشکل بود. چند هفته بعد معلوم شد بخشی از آن ورودی کاربر را بدون بررسی ذخیره می‌کند. امروز بخش بزرگی از سرعت من در ساختن سایت و اپلیکیشن از ابزارهای هوش مصنوعی می‌آید، ولی با یک قاعده سفت: هیچ کدی وارد پروژه نمی‌شود که خودم نفهمیده و بازبینی نکرده باشم. این درس روش کار من با هوش مصنوعی در برنامه‌نویسی وب است؛ جاهایی که واقعاً سرعت می‌دهد، جاهایی که خطرناک است و چک‌لیستی که قبل از قبول هر خروجی استفاده می‌کنم.

این درس پایانی دوره آموزش Next.js برای کسب‌وکار است و به همه درس‌های قبل ارجاع می‌دهد؛ چون بازبینی خروجی هوش مصنوعی بدون فهم همان مفاهیم ممکن نیست.

هوش مصنوعی کجا واقعاً سرعت می‌دهد؟

  • کد تکراری و قالبی: اسکلت کامپوننت، طرح اعتبارسنجی برای یک پاسخ JSON، فرم با چند فیلد، تست‌های ساده.
  • ترجمه بین زبان‌ها و نسخه‌ها: تبدیل یک تابع PHP به TypeScript، یا یک کامپوننت از Pages Router به App Router.
  • توضیح کد ناآشنا: وقتی پروژه‌ای را تحویل می‌گیرید و باید سریع بفهمید هر بخش چه می‌کند.
  • پیدا کردن علت خطا: با دادن پیام خطا، کد مرتبط و رفتار مورد انتظار.
  • نوشتن متن‌های فنی: توضیح Pull Request، مستند API و پیام‌های خطای قابل‌فهم برای کاربر.

کجا خطرناک است؟

مدل‌های زبانی کدی تولید می‌کنند که محتمل به نظر برسد، نه کدی که لزوماً درست، امن یا مناسب پروژه شما باشد. اشتباه‌هایی که بیشتر از همه در خروجی‌ها دیده‌ام:

  • الگوهای نسخه قدیمی: استفاده از getServerSideProps در App Router، یا params بدون await در نسخه‌های جدید Next.js.
  • رازها در سمت مرورگر: کلید API با پیشوند NEXT_PUBLIC_ یا فراخوانی مستقیم API بیرونی از Client Component. چرایی‌اش را در درس اتصال به API توضیح داده‌ام.
  • 'use client' بالای همه‌چیز: چون ساده‌ترین راه برای «کار کردن» است. نتیجه، از دست رفتن مزیت Server Component است؛ درس رندرینگ را ببینید.
  • اعتبارسنجی فقط سمت کاربر: فرمی که در مرورگر بررسی می‌شود ولی مسیر API هر ورودی را قبول می‌کند.
  • کتابخانه یا تابع خیالی: اسم پکیج یا متدی که وجود ندارد، یا بدتر، پکیجی با اسم مشابه که کسی دیگر منتشر کرده است.
  • مدیریت نکردن خطا: fetch بدون timeout و بدون بررسی res.ok.

چطور درخواست بدهیم تا خروجی بهتر بگیریم؟

کیفیت خروجی بیشتر از هر چیز به زمینه‌ای بستگی دارد که می‌دهید. درخواست «یک فرم تماس بساز» نتیجه‌ای عمومی می‌دهد. درخواستی که خودم می‌نویسم چیزی شبیه این است:

پروژه: Next.js 15 با App Router، TypeScript، Tailwind، سایت فارسی RTL.
قواعد: داده اولیه در Server Component؛ فقط بخش تعاملی 'use client'.
کلیدها فقط در متغیر محیطی سرور. اعتبارسنجی ورودی با zod هم در فرم و هم در route.ts.
کار: فرم درخواست مشاوره با فیلدهای نام و موبایل (09xxxxxxxxx)،
ارسال به app/api/leads/route.ts که 422 برای ورودی نامعتبر و 201 برای موفقیت برمی‌گرداند.
کد موجود مرتبط: [فایل‌های مرتبط را اینجا می‌گذارم]
خروجی: فقط فایل‌های تغییرکرده، با توضیح کوتاه هر تصمیم.

چند عادت دیگر که نتیجه را بهتر کرده‌اند:

  • کار بزرگ را به قدم‌های کوچک قابل‌بررسی تقسیم کنید؛ یک کامپوننت، یک مسیر، یک تست.
  • کد واقعی پروژه را بدهید تا الگوها و نام‌گذاری‌ها با بقیه کد یکی باشد.
  • از مدل بخواهید فرض‌هایش را بنویسد. فرض اشتباه را زودتر از کد اشتباه پیدا می‌کنید.
  • هیچ‌وقت کلید، رمز، اطلاعات مشتری یا داده محرمانه کارفرما را در درخواست نگذارید.

چک‌لیست بازبینی قبل از قبول هر خروجی

این چک‌لیست را برای هر کدی که از هوش مصنوعی می‌گیرم، مثل کد یک همکار تازه‌کار، اجرا می‌کنم:

  1. می‌فهمم هر خط چه می‌کند؟ اگر نه، یا توضیح می‌خواهم یا آن بخش را خودم می‌نویسم.
  2. ورودی‌ها کجا بررسی می‌شوند؟ سمت سرور، با نوع و محدوده مشخص.
  3. چه چیزی به مرورگر می‌رسد؟ هیچ راز، توکن یا داده‌ای که کاربر نباید ببیند.
  4. خطاها کجا مدیریت می‌شوند؟ timeout، کد وضعیت، پاسخ با فرمت غیرمنتظره، شبکه قطع.
  5. با نسخه فریم‌ورک پروژه سازگار است؟ مستندات رسمی را برای هر API ناآشنا چک می‌کنم.
  6. پکیج جدیدی اضافه شده؟ نام دقیق، تعداد نگهدارنده‌ها، آخرین به‌روزرسانی و اینکه واقعاً لازم است.
  7. تست یا حداقل اجرای دستی سناریوهای خطا انجام شده؟ نه فقط مسیر موفق.
  8. build تولید و lint بدون خطاست؟

تست: جایی که هوش مصنوعی بیشترین ارزش را دارد

یکی از بهترین استفاده‌ها، نوشتن تست برای کدی است که خودتان نوشته‌اید. از مدل بخواهید حالت‌های مرزی را پیدا کند: رشته خالی، شماره با ارقام فارسی، پاسخ API با فیلد گم‌شده، کاربر بدون دسترسی. حتی اگر همه تست‌های پیشنهادی را نگه ندارید، فهرست حالت‌ها خودش ارزشمند است. برعکس آن، یعنی گرفتن کد و تست از یک منبع و قبول هر دو بدون بازبینی، فقط به شما اطمینان کاذب می‌دهد.

حریم خصوصی و مالکیت کد

قبل از استفاده از هر ابزار هوش مصنوعی روی پروژه کارفرما، سه چیز را روشن کنید: قرارداد اجازه ارسال کد به سرویس بیرونی را می‌دهد یا نه، سرویس از داده شما برای آموزش استفاده می‌کند یا نه، و کدهای حساس (احراز هویت، پرداخت، داده مشتری) را با چه دقتی بازبینی می‌کنید. بسیاری از سرویس‌ها تنظیماتی برای خاموش کردن استفاده از داده در آموزش دارند؛ آن را بررسی کنید.

مهارتی که با هوش مصنوعی مهم‌تر شده

بیشترین تغییری که در کارم دیدم این است که وقت کمتری صرف تایپ و وقت بیشتری صرف تصمیم‌گیری و بازبینی می‌شود: معماری داده، مرز سرور و کلاینت، استراتژی کش، امنیت. این‌ها دقیقاً همان مفاهیم درس‌های این دوره‌اند. هوش مصنوعی کسی را که این‌ها را می‌فهمد خیلی سریع‌تر می‌کند و کسی را که نمی‌فهمد، سریع‌تر به باگ می‌رساند.

اگر می‌خواهید این چالش را به شکل بازی تجربه کنید، مرحله «ددلاین و AI» در بازی کوروش دیباگر دقیقاً همین است: تیکت‌ها را با کمک هوش مصنوعی سریع‌تر می‌بندید، ولی اگر خروجی باگ‌دار را بدون بازبینی قبول کنید، باگ به پروداکشن می‌رسد.

جمع‌بندی

هوش مصنوعی برای کد قالبی، توضیح، رفع خطا و تست شتاب‌دهنده‌ای واقعی است، به شرطی که زمینه کامل بدهید، کار را کوچک کنید و هر خروجی را با چک‌لیست بازبینی کنید. مسئولیت کدی که وارد پروژه می‌شود با شماست، نه با ابزاری که آن را نوشته است.

این آخرین درس دوره بود. درس قبل، دیپلوی Next.js روی سرور، و برای مرور کل مسیر راهنمای Next.js برای کسب‌وکار را ببینید. اگر کد پروژه‌تان را با کمک هوش مصنوعی یا بدون آن می‌نویسید، رعایت اصول استانداردهای مهندسی نرم‌افزار همچنان تعیین می‌کند پروژه بعد از یک سال قابل نگهداری باشد یا نه.

اگر برای ساخت وب‌اپ یا سایتی که سریع ساخته شود ولی کیفیت و امنیتش قابل اتکا باشد کمک می‌خواهید، فرم درخواست پروژه را پر کنید.
