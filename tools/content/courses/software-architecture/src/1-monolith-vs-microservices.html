وقتی پروژه‌ای از یک سایت ساده به وب‌اپلیکیشن می‌رسد، معمولاً کسی در جلسه پیشنهاد می‌دهد سیستم از اول به‌صورت میکروسرویس ساخته شود تا «مقیاس‌پذیر» باشد. این پیشنهاد گاهی درست است، ولی بیشتر وقت‌ها هزینه‌ای می‌سازد که تیم کوچک توان پرداختش را ندارد. این درس مقایسه می‌کند مونولیت، مونولیت ماژولار و معماری میکروسرویس هر کدام چه مسئله‌ای را حل می‌کنند و مهم‌تر از آن، کی نباید سیستم را شکست.

این درس اول دوره معماری نرم‌افزار برای وب‌اپ‌های کسب‌وکار است.

سه سبک، به زبان ساده

مونولیت یعنی کل سیستم یک برنامه است که یک بار build و دیپلوی می‌شود و معمولاً یک دیتابیس دارد. بیشتر سایت‌های وردپرسی، پروژه‌های لاراول و جنگو و بسیاری از اپ‌های Next.js مونولیت‌اند. این به خودی خود ایراد نیست.

مونولیت ماژولار همان مونولیت است با یک تفاوت مهم: کد به ماژول‌هایی با مرز روشن تقسیم شده، مثل کاربران، سفارش، پرداخت و اعلان‌ها. هر ماژول جدول‌ها و منطق خودش را دارد و بقیه فقط از طریق رابط عمومی‌اش با آن کار می‌کنند.

میکروسرویس یعنی هر بخش یک برنامه مستقل است، با دیپلوی و معمولاً دیتابیس خودش، و بخش‌ها از طریق شبکه، با API یا پیام، با هم ارتباط می‌گیرند.

هزینه واقعی شکستن سیستم

میکروسرویس مزایای واقعی دارد، ولی هزینه‌هایش کمتر در مقاله‌های معرفی دیده می‌شود. وقتی یک فراخوانی تابع به یک درخواست شبکه تبدیل می‌شود، این چیزها به پروژه اضافه می‌شود:

  • خطای شبکه. فراخوانی تابع یا اجرا می‌شود یا استثنا می‌دهد. درخواست شبکه می‌تواند کند شود، timeout بخورد یا انجام شود ولی پاسخش نرسد. برای هر فراخوانی باید timeout، تلاش دوباره و رفتار هنگام قطعی طراحی شود.
  • داده توزیع‌شده. وقتی سفارش و موجودی در دو دیتابیس جدا هستند، دیگر نمی‌شود با یک تراکنش هر دو را با هم تغییر داد. باید الگوهایی مثل saga یا outbox را پیاده کرد و حالت‌های نیمه‌کاره را مدیریت کرد.
  • عملیات و پایش. هر سرویس دیپلوی، لاگ، متریک، هشدار و به‌روزرسانی وابستگی‌های خودش را می‌خواهد. پیدا کردن علت یک خطا بدون ردیابی توزیع‌شده می‌تواند ساعت‌ها طول بکشد.
  • نسخه‌بندی قراردادها. تغییر یک تابع داخلی با یک refactor انجام می‌شود؛ تغییر API بین دو سرویس باید سازگار با نسخه قبلی باشد تا دیپلوی‌ها به هم گره نخورند.
  • محیط توسعه. اجرای کل سیستم روی لپ‌تاپ توسعه‌دهنده یا ساختن محیط تست کامل، با ده سرویس به‌مراتب سخت‌تر از یک برنامه است.

هیچ‌کدام از این‌ها حل‌نشدنی نیست، ولی هر کدام زمان مهندسی می‌خواهد. برای تیمی سه‌نفره که باید قابلیت تحویل بدهد، این زمان معمولاً از ساختن خود محصول کم می‌شود.

میکروسرویس کی واقعاً جواب می‌دهد؟

میکروسرویس بیش از هر چیز مسئله سازمانی را حل می‌کند: وقتی چند تیم مستقل روی یک سیستم کار می‌کنند و هماهنگی دیپلوی‌هایشان به گلوگاه تبدیل شده است. علاوه بر آن، چند دلیل فنی مشخص هم وجود دارد:

  • بخشی از سیستم باری کاملاً متفاوت دارد، مثلاً پردازش ویدئو یا تصویر که CPU زیادی می‌خواهد، و نباید روی سرعت بقیه سیستم اثر بگذارد.
  • بخشی نیاز امنیتی یا انطباقی جدا دارد، مثلاً پردازش پرداخت که باید دسترسی محدودتر و سطح ممیزی بالاتری داشته باشد.
  • بخشی باید با زبان یا فناوری دیگری نوشته شود، مثلاً مدل یادگیری ماشین در پایتون کنار اپ اصلی در جاوااسکریپت.
  • چرخه انتشار بخشی با بقیه کاملاً متفاوت است و انتظار برای دیپلوی کل سیستم مانع کار می‌شود.

دقت کنید که «ممکن است روزی ترافیکمان زیاد شود» در این فهرست نیست. مونولیت را می‌شود با اجرای چند نمونه پشت لود بالانسر، کش و بهینه‌سازی دیتابیس برای ترافیک زیادی مقیاس داد. این موضوع در مقاله سرعت سمت سرور و معماری مقیاس‌پذیر هم بررسی شده است.

ساختن مونولیت ماژولار در عمل

مونولیت ماژولار فقط یک تصمیم نیست؛ مجموعه‌ای از قواعد است که باید در کد رعایت شود. یک ساختار پوشه نمونه برای وب‌اپ TypeScript:

src/
  modules/
    users/
      index.ts        // public API of the module (the only allowed import)
      service.ts
      repository.ts
    orders/
      index.ts
      service.ts
      repository.ts
      events.ts       // events other modules may listen to
    payments/
    notifications/
  shared/             // small, stable helpers only (money, dates, errors)
  app/                // routes / controllers: call module index files only

قواعدی که این ساختار را معنادار می‌کنند:

  1. هر ماژول فقط از index ماژول دیگر import می‌کند. import مستقیم از فایل‌های داخلی یک ماژول دیگر ممنوع است. این قاعده را می‌شود با ابزارهایی مثل قوانین lint برای مرز importها خودکار بررسی کرد.
  2. هر ماژول مالک جدول‌های خودش است. ماژول سفارش مستقیم در جدول کاربران نمی‌نویسد و از آن نمی‌خواند؛ از users.getById() استفاده می‌کند.
  3. ارتباط‌های غیرضروری هم‌زمان را با رویداد جایگزین کنید. ماژول سفارش لازم نیست بداند بعد از ثبت سفارش پیامک می‌رود؛ رویداد «سفارش ثبت شد» را منتشر می‌کند و ماژول اعلان‌ها به آن گوش می‌دهد.
  4. پوشه shared کوچک بماند. اگر هر چیزی به shared منتقل شود، عملاً مرزی باقی نمی‌ماند.

اگر روزی لازم شد ماژول اعلان‌ها به سرویس جدا تبدیل شود، چون از قبل مرز و رابط روشن دارد، این کار به‌جای بازنویسی، یک جابه‌جایی کنترل‌شده است.

مسیر جداسازی تدریجی: الگوی Strangler Fig

اگر سیستمی قدیمی و درهم دارید، وسوسه بازنویسی کامل زیاد است. تجربه رایج صنعت این است که بازنویسی کامل معمولاً بیشتر از برآورد طول می‌کشد و در این مدت، سیستم قدیمی هم باید نگهداری شود. الگوی Strangler Fig راه کم‌خطرتری است:

  1. یک لایه مسیریاب، مثل reverse proxy یا API gateway، جلوی سیستم قدیمی می‌گذارید.
  2. یک قابلیت مشخص و کم‌وابسته را در سیستم یا ماژول جدید می‌سازید.
  3. مسیریاب درخواست‌های همان قابلیت را به بخش جدید می‌فرستد و بقیه همچنان به سیستم قدیمی می‌روند.
  4. بعد از پایدار شدن، قابلیت بعدی را منتقل می‌کنید و کد قدیمی را حذف می‌کنید.

این الگو مخصوصاً برای سایت‌های وردپرسی که بخشی از آن‌ها به اپ جدا منتقل می‌شود کاربرد دارد. نمونه‌اش ساختن بخش پویای سایت با Next.js در کنار محتوای وردپرس است که در مقاله وردپرس Headless با Next.js بررسی شده است.

نشانه‌های هشدار در هر دو طرف

هم مونولیت بی‌نظم و هم میکروسرویس زودهنگام نشانه‌های قابل تشخیص دارند:

  • مونولیت درهم: تغییر در بخش سفارش، باگ در بخش گزارش می‌سازد؛ هیچ‌کس نمی‌داند یک جدول را چه بخش‌هایی تغییر می‌دهند؛ اجرای تست‌ها یا build به‌طور مداوم طولانی‌تر می‌شود.
  • میکروسرویس توزیع‌شده درهم: برای انتشار یک قابلیت باید چند سرویس را با هم و به ترتیب خاص دیپلوی کنید؛ سرویس‌ها از یک دیتابیس مشترک می‌خوانند؛ یک درخواست کاربر زنجیره‌ای از پنج فراخوانی هم‌زمان بین سرویس‌ها می‌سازد.

حالت دوم گاهی «مونولیت توزیع‌شده» نامیده می‌شود: همه هزینه‌های میکروسرویس را دارد و هیچ‌کدام از مزایایش را ندارد.

جمع‌بندی

انتخاب بین مونولیت و معماری میکروسرویس بیشتر به اندازه تیم و نیازهای واقعی بستگی دارد تا به ترافیک. برای بیشتر وب‌اپ‌های کسب‌وکار، مونولیت ماژولار با مرزهای روشن، مالکیت داده برای هر ماژول و ارتباط رویدادی بین ماژول‌ها بهترین شروع است. جداسازی را وقتی شروع کنید که دلیل مشخصی مثل بار متفاوت، نیاز امنیتی جدا یا استقلال تیم‌ها دارید، و آن را تدریجی انجام دهید.

درس بعد، طراحی API قابل اعتماد، به قراردادی می‌پردازد که بخش‌ها و کلاینت‌ها از طریق آن با هم حرف می‌زنند. نقشه کامل دوره در راهنمای معماری نرم‌افزار است.

اگر نمی‌دانید سیستم فعلی‌تان را باید ماژولار کنید، بازنویسی کنید یا بخشی از آن را جدا کنید، فرم درخواست پروژه را پر کنید تا با هم بررسی کنیم.
