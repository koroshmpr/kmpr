API برای کسی که آن را می‌سازد فقط چند مسیر و تابع است، ولی برای کسی که از آن استفاده می‌کند، یک قرارداد است. اپ موبایلی که ماه‌ها پیش منتشر شده، پنل همکاری که شرکت دیگری ساخته و اسکریپتی که هر شب گزارش می‌گیرد، همه به این قرارداد تکیه کرده‌اند. طراحی API خوب یعنی این قرارداد قابل پیش‌بینی، مستند و پایدار باشد تا هر تغییر سمت سرور، چیزی را در جای دیگری بی‌صدا خراب نکند.

این درس دوم دوره معماری نرم‌افزار برای وب‌اپ‌های کسب‌وکار است و تمرکزش روی REST روی HTTP است، چون برای بیشتر وب‌اپ‌های کسب‌وکار ساده‌ترین و پرکاربردترین انتخاب است.

منابع و متدها: اسم در آدرس، فعل در متد

در REST هر داده‌ای که کلاینت با آن کار می‌کند یک «منبع» است با آدرس مشخص. قاعده اصلی این است که آدرس، اسم منبع را می‌گوید و متد HTTP، عملیات را:

GET    /v1/orders              list orders (paginated)
POST   /v1/orders              create an order
GET    /v1/orders/123          read one order
PATCH  /v1/orders/123          partial update
DELETE /v1/orders/123          delete / cancel
GET    /v1/customers/45/orders orders of one customer

# avoid: verbs in the path
POST   /v1/createOrder
GET    /v1/getOrderById?id=123

چند قاعده تکمیلی:

  • اسم منبع‌ها جمع و با حروف کوچک باشد و یک سبک نام‌گذاری برای فیلدها انتخاب کنید (مثلاً snake_case) و همه جا رعایتش کنید.
  • GET هرگز داده را تغییر نمی‌دهد. مرورگرها، کش‌ها و خزنده‌ها فرض می‌کنند GET امن است و ممکن است آن را خودکار تکرار کنند.
  • PUT کل منبع را جایگزین می‌کند و PATCH فقط فیلدهای فرستاده‌شده را تغییر می‌دهد. برای فرم‌های ویرایش معمولاً PATCH مناسب‌تر است.
  • برای عملیاتی که در قالب ساخت و ویرایش نمی‌گنجد، مثل لغو سفارش، می‌شود آن را به شکل زیرمنبع یا اقدام تعریف کرد: POST /v1/orders/123/cancel. مهم این است که این استثنا مستند و یکدست باشد.

کد وضعیت درست، رفتار درست کلاینت

کد وضعیت HTTP فقط برای نمایش نیست؛ کلاینت با آن تصمیم می‌گیرد تلاش دوباره کند، کاربر را به صفحه ورود ببرد یا خطای فرم نشان دهد. برگرداندن 200 با یک فیلد "error" در بدنه، این تصمیم‌گیری را خراب می‌کند.

قالب یکسان برای همه خطاها

کلاینتی که با API شما کار می‌کند نباید برای هر مسیر، شکل متفاوتی از خطا را پردازش کند. یک قالب ثابت تعریف کنید و همه جا از آن استفاده کنید. استاندارد application/problem+json (RFC 9457) یک گزینه آماده است؛ یک قالب ساده‌تر هم کافی است به شرط ثبات:

HTTP/1.1 422 Unprocessable Content
Content-Type: application/json

{
  "error": {
    "code": "insufficient_stock",
    "message": "موجودی این محصول کافی نیست.",
    "details": [
      { "field": "items[0].quantity", "code": "max", "max": 2 }
    ],
    "request_id": "req_8f2c1a"
  }
}
  • code برای ماشین است و هرگز عوض نمی‌شود؛ کلاینت بر اساس آن تصمیم می‌گیرد.
  • message برای نمایش به کاربر است و می‌تواند فارسی باشد.
  • request_id همان شناسه‌ای است که در لاگ سرور ثبت شده؛ وقتی مشتری خطا را گزارش می‌دهد، با آن مستقیم به لاگ مربوط می‌رسید.
  • جزئیات داخلی مثل stack trace یا متن خطای دیتابیس هرگز در پاسخ نیاید.

صفحه‌بندی، فیلتر و مرتب‌سازی

هیچ فهرستی را بدون صفحه‌بندی برنگردانید. جدولی که امروز پنجاه رکورد دارد، سال بعد پنجاه هزار رکورد خواهد داشت و همان مسیر، سرور و کلاینت را با هم کند می‌کند. دو روش رایج:

  • offset/limit (مثل ?page=3&per_page=20): ساده و مناسب جدول‌های مدیریتی که کاربر به صفحه مشخص می‌رود. در صفحه‌های عمیق کند می‌شود و اگر وسط مرور رکورد جدیدی اضافه شود، ممکن است آیتمی تکرار یا جا بیفتد.
  • cursor (مثل ?after=eyJpZCI6MTIzfQ&limit=20): کلاینت نشانگر آخرین آیتم را می‌فرستد و سرور از بعد از آن ادامه می‌دهد. برای فیدها، اسکرول بی‌پایان و همگام‌سازی پایدارتر و سریع‌تر است.
GET /v1/orders?status=paid&sort=-created_at&limit=20

{
  "data": [ { "id": "ord_981", "status": "paid", "total_rial": 18500000 } ],
  "next_cursor": "eyJjcmVhdGVkX2F0IjoiMjAyNi0xMS0xOVQxMDowMDowMFoiLCJpZCI6OTgxfQ",
  "has_more": true
}

همیشه برای limit سقف بگذارید و فیلدهای قابل فیلتر و مرتب‌سازی را محدود و مستند کنید؛ مرتب‌سازی دلخواه روی هر ستون، دری برای پرس‌وجوهای بسیار کند است.

نسخه‌بندی و تغییرات سازگار

همه تغییرات نسخه جدید نمی‌خواهند. قاعده ساده این است:

  • سازگار (بدون نسخه جدید): اضافه کردن مسیر جدید، فیلد جدید در پاسخ، پارامتر اختیاری جدید.
  • ناسازگار (نسخه جدید): حذف یا تغییر نام فیلد، تغییر نوع یا واحد آن، اجباری کردن پارامتری که اختیاری بود، تغییر معنای یک کد وضعیت.

نسخه در آدرس (/v1/) ساده‌ترین روش است. وقتی /v2/ منتشر شد، نسخه قبلی را با اعلام زمان مشخص و هدرهایی مثل Deprecation و Sunset کنار بگذارید و قبل از خاموش کردن، از لاگ‌ها بررسی کنید چه کسی هنوز از آن استفاده می‌کند. کلاینت‌ها هم باید طوری نوشته شوند که فیلدهای ناشناخته را نادیده بگیرند، نه اینکه با آن‌ها خطا بدهند.

idempotency: وقتی درخواست دو بار می‌رسد

کاربر روی «پرداخت» می‌زند، اینترنتش لحظه‌ای قطع می‌شود و اپ درخواست را دوباره می‌فرستد. اگر سرور نداند این همان درخواست قبلی است، دو سفارش ثبت می‌شود یا دو بار از کیف پول کم می‌شود. GET، PUT و DELETE طبق تعریف idempotent هستند، ولی POST نیست و باید امنش کرد:

POST /v1/orders
Idempotency-Key: 3f9a2b7e-1c4d-4e8f-9a6b-2d5c7e8f1a3b

// server (pseudo-code)
const saved = await idem.find(userId, key);
if (saved) {
  if (saved.requestHash !== hash(body)) return conflict(409);
  return replay(saved.status, saved.body);     // same answer, no second order
}
const result = await createOrder(body);          // inside a DB transaction
await idem.save(userId, key, hash(body), result); // unique (user_id, key), expires after 24h
return result;

کلید را کلاینت برای هر عمل کاربر یک بار می‌سازد و در تلاش‌های دوباره همان را می‌فرستد. روی ستون‌های (user_id, key) قید یکتا بگذارید تا دو درخواست هم‌زمان هم نتوانند هر دو ثبت شوند. همین منطق در اتصال درگاه پرداخت هم لازم است که در درس اتصال درگاه پرداخت ایرانی از دوره فروش آنلاین توضیح داده شده است.

احراز هویت، محدودسازی و مستندسازی

  • احراز هویت: برای وب‌اپ با مرورگر، نشست با کوکی HttpOnly؛ برای اپ موبایل و سرویس‌ها، توکن در هدر Authorization: Bearer؛ برای همکاران، کلید API جداگانه برای هر همکار با امکان باطل کردن. توکن یا کلید هرگز در آدرس (query string) نیاید، چون در لاگ‌ها ثبت می‌شود.
  • مجوز روی هر منبع: اینکه کاربر وارد شده کافی نیست؛ باید بررسی شود سفارش ۱۲۳ متعلق به همین کاربر است. این موضوع در درس امنیت وب‌اپلیکیشن مفصل آمده است.
  • محدودسازی نرخ: برای هر کاربر یا کلید سقف درخواست بگذارید و هنگام عبور از آن 429 با هدر Retry-After برگردانید.
  • مستندسازی: قرارداد را با OpenAPI بنویسید. از همان فایل می‌شود مستندات قابل مرور، کلاینت تولیدشده و تست قرارداد ساخت.

جمع‌بندی

طراحی API خوب یعنی قراردادی که مصرف‌کننده بتواند بدون حدس زدن با آن کار کند: منابع با اسم و متدهای درست، کد وضعیت دقیق، قالب خطای ثابت با کد ماشینی و شناسه درخواست، صفحه‌بندی با سقف، نسخه‌بندی برای تغییرات ناسازگار، کلید idempotency برای عملیات حساس و احراز هویت و مجوز روی هر درخواست. این قواعد هزینه کمی در ابتدا دارند و جلوی بخش بزرگی از باگ‌های یکپارچه‌سازی را می‌گیرند.

درس قبل مونولیت یا معماری میکروسرویس بود. درس بعد، طراحی دیتابیس و مدل‌سازی داده، به لایه‌ای می‌رود که این API روی آن ساخته می‌شود. نقشه کامل دوره در راهنمای معماری نرم‌افزار است.

اگر برای وب‌اپ، اپ موبایل یا همکارانتان API لازم دارید یا باید سیستمتان را به درگاه، CRM یا سرویس دیگری وصل کنید، فرم درخواست پروژه را پر کنید.
