کد یک وب‌اپ ممکن است چند بار بازنویسی شود، فریم‌ورکش عوض شود یا رابط کاربری‌اش از نو طراحی شود، ولی داده مشتری‌ها، سفارش‌ها و تراکنش‌ها باید سال‌ها سالم و قابل اعتماد بماند. به همین دلیل طراحی دیتابیس یکی از تصمیم‌هایی است که بیشترین اثر بلندمدت را دارد. مبلغی که با اعشار ذخیره شده، تاریخی که منطقه زمانی ندارد یا نام مشتری که در پنج جدول تکرار شده، معمولاً ماه‌ها بعد به شکل گزارش اشتباه یا باگ عجیب خودش را نشان می‌دهد.

این درس سوم دوره معماری نرم‌افزار برای وب‌اپ‌های کسب‌وکار است. مثال‌ها با SQL و PostgreSQL نوشته شده‌اند، ولی اصول برای MySQL و دیتابیس‌های رابطه‌ای دیگر هم صادق است.

مدل داده را از زبان کسب‌وکار دربیاورید

اشتباه رایج این است که جدول‌ها از روی صفحه‌های طراحی ساخته شوند: «صفحه پروفایل این فیلدها را دارد، پس جدول پروفایل». روش بهتر این است که با صاحب کسب‌وکار صحبت کنید و اسم‌ها و قواعد را از زبان خود او دربیاورید:

  • موجودیت‌ها: چه چیزهایی ثبت و پیگیری می‌شوند؟ مشتری، محصول، سفارش، پرداخت، ارسال.
  • رابطه‌ها: هر مشتری چند سفارش دارد؛ هر سفارش چند قلم کالا؛ هر کالا ممکن است در چند سفارش باشد.
  • قواعد: سفارش پرداخت‌شده قابل حذف نیست؛ شماره موبایل هر مشتری یکتاست؛ موجودی منفی نمی‌شود.
  • چرخه حیات: سفارش از چه وضعیت‌هایی می‌گذرد و کدام تغییر وضعیت مجاز است؟

یک نکته مهم: قیمت و مشخصات محصول در لحظه خرید باید در خود قلم سفارش ذخیره شود. اگر سفارش فقط به شناسه محصول اشاره کند و قیمت را از جدول محصول بخواند، با تغییر قیمت فردا، فاکتورهای دیروز هم عوض می‌شوند.

نرمال‌سازی: هر واقعیت فقط یک جا

نرمال‌سازی یعنی هر اطلاعات فقط یک بار ذخیره شود و بقیه جاها به آن اشاره کنند. فرض کنید نام و موبایل مشتری در جدول سفارش هم کپی شده باشد؛ مشتری که شماره‌اش را عوض کند، در بعضی گزارش‌ها با شماره قدیم و در بعضی با شماره جدید دیده می‌شود. نمونه یک طرح نرمال:

CREATE TABLE customers (
  id          bigserial PRIMARY KEY,
  mobile      varchar(11) NOT NULL UNIQUE,
  full_name   text NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE orders (
  id           bigserial PRIMARY KEY,
  customer_id  bigint NOT NULL REFERENCES customers(id),
  status       text NOT NULL CHECK (status IN ('pending','paid','shipped','cancelled')),
  total_rial   bigint NOT NULL CHECK (total_rial >= 0),
  created_at   timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE order_items (
  order_id         bigint NOT NULL REFERENCES orders(id),
  product_id       bigint NOT NULL REFERENCES products(id),
  title_snapshot   text NOT NULL,      -- product title at purchase time
  unit_price_rial  bigint NOT NULL,    -- price at purchase time
  quantity         int NOT NULL CHECK (quantity > 0),
  PRIMARY KEY (order_id, product_id)
);

نرمال‌سازی هدف مطلق نیست. گاهی برای سرعت گزارش یا جلوگیری از join سنگین، داده آگاهانه تکرار می‌شود؛ مثلاً جمع کل سفارش در خود سفارش ذخیره می‌شود. قاعده این است که این تکرار با دلیل مشخص باشد و یک جای مشخص مسئول به‌روز نگه داشتنش باشد.

قیدها: قواعد را به دیتابیس بسپارید

اعتبارسنجی در کد لازم است، ولی کافی نیست. اسکریپت مهاجرت داده، یک مسیر API که کسی فراموش کرده چک کند، یا دو درخواست هم‌زمان می‌توانند از آن عبور کنند. دیتابیس آخرین خط دفاع است:

  • NOT NULL برای فیلدهایی که همیشه باید مقدار داشته باشند.
  • UNIQUE برای یکتایی واقعی، مثل موبایل مشتری یا کد تخفیف. شرط if (!exists) insert در کد، با دو درخواست هم‌زمان می‌شکند؛ قید یکتا نه.
  • FOREIGN KEY تا سفارشی به مشتری ناموجود اشاره نکند.
  • CHECK برای قواعد ساده، مثل مبلغ نامنفی یا وضعیت از فهرست مجاز.

برای عملیاتی که چند جدول را با هم تغییر می‌دهد، مثل ثبت سفارش و کم کردن موجودی، از تراکنش استفاده کنید تا یا همه تغییرات انجام شوند یا هیچ‌کدام. برای جلوگیری از فروش بیش از موجودی، کم کردن را به شکل شرطی و اتمی بنویسید:

UPDATE products
SET stock = stock - 2
WHERE id = 77 AND stock >= 2;
-- 0 rows updated  ->  not enough stock, roll back the order

نوع داده درست برای پول، زمان و شناسه

بخش زیادی از باگ‌های داده از انتخاب نوع اشتباه می‌آید:

دادهانتخاب درستاشتباه رایج
مبلغعدد صحیح (bigint) در کوچک‌ترین واحد، با واحد در نام ستونfloat که خطای گرد کردن دارد؛ ابهام ریال و تومان
زمانtimestamptz و ذخیره در UTC؛ تبدیل به شمسی و وقت تهران فقط هنگام نمایشرشته تاریخ شمسی؛ زمان بدون منطقه زمانی
موبایل و کد ملیرشته با فرمت یکسان و ارقام لاتینعدد که صفر اول را حذف می‌کند
وضعیتمقدار از فهرست مشخص با CHECK یا enumمتن آزاد با املای متفاوت
شناسه عمومیشناسه غیرقابل حدس (مثل UUID) در آدرس‌های عمومیشناسه ترتیبی که تعداد سفارش‌ها را لو می‌دهد

ذخیره تاریخ به شکل شمسی در دیتابیس، مرتب‌سازی، محاسبه فاصله زمانی و ارتباط با هر سیستم دیگر را سخت می‌کند. داده را با ارقام لاتین و استاندارد نگه دارید و فقط در لایه نمایش فارسی و شمسی کنید.

ایندکس: برای پرس‌وجوهای واقعی

ایندکس مثل فهرست انتهای کتاب است: پیدا کردن را سریع می‌کند، ولی هر بار که چیزی اضافه یا تغییر می‌کند، فهرست هم باید به‌روز شود. پس ایندکس روی هر ستون راه‌حل نیست. روش درست این است که پرس‌وجوهای پرتکرار و کند را پیدا کنید و برای آن‌ها ایندکس بسازید:

-- frequent query: a customer's recent orders
SELECT id, status, total_rial, created_at
FROM orders
WHERE customer_id = 45
ORDER BY created_at DESC
LIMIT 20;

-- matching composite index (column order matters)
CREATE INDEX orders_customer_created_idx ON orders (customer_id, created_at DESC);

-- verify the plan uses it
EXPLAIN ANALYZE SELECT ...;
  • ترتیب ستون‌ها در ایندکس ترکیبی مهم است: ستون‌های شرط برابری اول، ستون مرتب‌سازی یا بازه بعد.
  • ستون‌های کلید خارجی که در join یا فیلتر استفاده می‌شوند، معمولاً ایندکس لازم دارند. PostgreSQL این ایندکس را خودکار نمی‌سازد.
  • لاگ پرس‌وجوهای کند (slow query log) را فعال کنید تا بدانید کدام پرس‌وجو واقعاً مشکل دارد.
  • مراقب مسئله N+1 در ORMها باشید: صد پرس‌وجوی کوچک در یک حلقه، به‌جای یک پرس‌وجو با join.

مایگریشن: تغییر ساختار بدون دستور دستی

هر تغییر در ساختار دیتابیس باید یک فایل مایگریشن نسخه‌دار در گیت باشد که با ابزار فریم‌ورک (مثل مایگریشن‌های لاراول، جنگو، Prisma یا Drizzle) به ترتیب روی محیط توسعه، تست و اصلی اجرا شود. دستور ALTER TABLE که کسی مستقیم روی سرور اصلی اجرا کرده، ساختار محیط‌ها را از هم جدا می‌کند و تکرار پذیر نیست.

برای تغییر بدون قطعی در سیستمی که کاربر فعال دارد، الگوی «گسترش و جمع کردن» (expand and contract) را به کار ببرید. مثلاً برای تغییر نام یک ستون:

  1. ستون جدید را اضافه کنید (کد قدیمی همچنان کار می‌کند).
  2. کد را طوری دیپلوی کنید که در هر دو ستون بنویسد.
  3. داده قدیمی را در دسته‌های کوچک به ستون جدید کپی کنید.
  4. کد را طوری دیپلوی کنید که فقط از ستون جدید بخواند.
  5. در مایگریشن بعدی، ستون قدیمی را حذف کنید.

روی جدول‌های بزرگ، بعضی تغییرات مثل ساختن ایندکس یا اضافه کردن ستون با مقدار پیش‌فرض ممکن است جدول را قفل کنند. در PostgreSQL برای ایندکس از CREATE INDEX CONCURRENTLY استفاده کنید و همیشه مایگریشن را اول روی کپی داده واقعی تست کنید.

بکاپ، بازگردانی و داده حساس

مدل داده هر قدر خوب باشد، بدون بکاپ قابل بازگردانی، یک حادثه یا یک دستور اشتباه می‌تواند همه چیز را از بین ببرد. حداقل‌های لازم:

  • بکاپ خودکار و منظم، در جایی جدا از سرور اصلی و با نسخه‌های قدیمی‌تر.
  • برای دیتابیس‌های پرتغییر، بکاپ پیوسته یا لاگ تراکنش (مثل WAL در PostgreSQL) تا بشود به یک لحظه مشخص برگشت.
  • تست دوره‌ای بازگردانی روی سرور جدا؛ بکاپی که ریستورش امتحان نشده، فقط امید است.
  • رمزگذاری بکاپ‌ها و محدود کردن دسترسی به آن‌ها، چون یک کپی کامل از داده مشتری‌هاست.

مفاهیمی مثل قاعده ۳-۲-۱، RPO و RTO در مقاله استراتژی بکاپ و بازگردانی سایت از دوره امنیت و نگهداری توضیح داده شده‌اند. اگر روی وردپرس کار می‌کنید، مقاله مدل‌سازی محتوا در وردپرس نسخه همین فکر برای محتواست.

جمع‌بندی

طراحی دیتابیس خوب با فهم کسب‌وکار شروع می‌شود، نه با صفحه‌ها. هر واقعیت را یک جا ذخیره کنید و قیمت لحظه خرید را در سفارش نگه دارید، قواعد مهم را با قیدها و تراکنش در خود دیتابیس تضمین کنید، پول را عدد صحیح و زمان را UTC ذخیره کنید، ایندکس را برای پرس‌وجوهای واقعی بسازید، هر تغییر ساختار را با مایگریشن نسخه‌دار انجام دهید و بکاپ را با بازگردانی واقعی بسنجید.

درس قبل طراحی API قابل اعتماد بود. درس بعد، کش، صف پیام و کارهای پس‌زمینه، نشان می‌دهد چطور کارهای کند را از مسیر درخواست کاربر بیرون ببرید. نقشه کامل دوره در راهنمای معماری نرم‌افزار است.

اگر وب‌اپ یا پنلی دارید که داده‌اش به‌هم‌ریخته شده یا می‌خواهید سیستم جدیدی را از ابتدا درست طراحی کنید، فرم درخواست پروژه را پر کنید.
