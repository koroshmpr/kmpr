کاربری که روی «ثبت سفارش» می‌زند، نباید منتظر بماند تا پیامک تأیید ارسال شود، فاکتور PDF ساخته شود و اطلاعات به CRM برود. اگر همه این کارها داخل همان درخواست انجام شوند، کندی هر کدام صفحه کاربر را کند می‌کند و قطعی هر کدام ممکن است کل سفارش را با خطا مواجه کند. راه‌حل معماری این است که کارهای کند و وابسته به سرویس بیرونی به صف پیام سپرده شوند و جداگانه انجام شوند، و داده‌هایی که زیاد خوانده می‌شوند با قاعده روشن کش شوند.

این درس چهارم دوره معماری نرم‌افزار برای وب‌اپ‌های کسب‌وکار است. بخش سرعت پاسخ سرور و کش صفحه در مقاله سرعت سمت سرور و معماری مقیاس‌پذیر آمده و این درس روی کارهای پس‌زمینه و پایداری تمرکز دارد.

صف پیام و worker چطور کار می‌کنند؟

الگو سه جزء دارد. تولیدکننده (کد درخواست کاربر) یک پیام شامل نوع کار و داده لازم در صف می‌گذارد. صف پیام‌ها را نگه می‌دارد. worker یک فرایند جداست که پیام‌ها را برمی‌دارد، کار را انجام می‌دهد و در پایان موفقیت را تأیید می‌کند. اگر تأیید نرسد، صف پیام را دوباره در دسترس قرار می‌دهد.

// producer: inside the order request (Node.js + BullMQ on Redis)
import { Queue } from 'bullmq';
const notify = new Queue('notifications', { connection });

await db.orders.insert(order);
await notify.add('order-sms',
  { orderId: order.id },
  { jobId: `order-sms:${order.id}`,          // same job is never queued twice
    attempts: 5,
    backoff: { type: 'exponential', delay: 10_000 },
    removeOnComplete: 1000 });

// worker: a separate process
import { Worker } from 'bullmq';
new Worker('notifications', async (job) => {
  const order = await db.orders.find(job.data.orderId); // read fresh data
  if (order.sms_sent_at) return;                         // already done: skip
  await sms.send(order.customer_mobile, smsText(order));
  await db.orders.update(order.id, { sms_sent_at: new Date() });
}, { connection, concurrency: 5 });

ابزار به زبان و زیرساخت بستگی دارد: BullMQ روی Redis در Node.js، صف‌های لاراول، Celery در پایتون، RabbitMQ یا سرویس‌های صف ابری. برای شروع در پروژه کوچک، حتی یک جدول jobs در همان دیتابیس با یک worker که با SELECT ... FOR UPDATE SKIP LOCKED کار برمی‌دارد، کافی است و نیاز به سرویس جدیدی ندارد.

یک نکته در کد بالا مهم است: در پیام فقط شناسه سفارش آمده، نه کل داده. worker داده تازه را از دیتابیس می‌خواند؛ چون ممکن است بین ثبت پیام و اجرای کار، سفارش لغو یا ویرایش شده باشد.

«حداقل یک بار» یعنی کارها باید idempotent باشند

بیشتر صف‌ها تضمین «حداقل یک بار» می‌دهند، نه «دقیقاً یک بار». اگر worker پیامک را بفرستد و درست قبل از تأیید کار از کار بیفتد، همان کار دوباره اجرا می‌شود. پس هر کار باید طوری نوشته شود که اجرای دوباره‌اش اثر دوباره نداشته باشد:

  • قبل از انجام، وضعیت را چک کنید (مثل sms_sent_at در مثال بالا).
  • برای سرویس‌های بیرونی که کلید idempotency می‌پذیرند، یک کلید ثابت بر اساس شناسه کار بفرستید.
  • برای ثبت نتیجه از قید یکتا استفاده کنید تا دو اجرای هم‌زمان نتوانند هر دو ثبت شوند.

این همان مفهومی است که در درس طراحی API قابل اعتماد برای درخواست‌های تکراری دیدیم؛ این بار سمت worker.

تلاش دوباره، فاصله افزایشی و صف خطا

سرویس‌های بیرونی گاهی موقتاً در دسترس نیستند. تلاش دوباره فوری و پشت سر هم، فقط فشار را روی سرویسی که مشکل دارد بیشتر می‌کند. سیاست درست:

  • فاصله افزایشی با کمی تصادف (exponential backoff with jitter): مثلاً ۱۰ ثانیه، ۲۰، ۴۰ و همین‌طور، تا همه کارهای شکست‌خورده هم‌زمان دوباره هجوم نیاورند.
  • تفکیک خطاها: خطای موقت (timeout، ۵۰۲، ۵۰۳، ۴۲۹) ارزش تلاش دوباره دارد؛ خطای دائمی (شماره نامعتبر، ۴۰۰، ۴۰۱) نه. کاری که هرگز موفق نمی‌شود را بی‌نهایت تکرار نکنید.
  • سقف تلاش و صف خطا (dead letter queue): بعد از چند تلاش، کار به صف جداگانه می‌رود، هشدار داده می‌شود و کسی بررسی‌اش می‌کند. پنلی برای دیدن و اجرای دوباره این کارها خیلی کمک می‌کند.
  • timeout برای هر فراخوانی بیرونی: workerی که بی‌نهایت منتظر یک سرویس بماند، صف را متوقف می‌کند.

الگوی outbox: پیامی که گم نمی‌شود

در کد تولیدکننده بالا یک مشکل پنهان هست: اگر سفارش در دیتابیس ذخیره شود و درست قبل از افزودن پیام به صف، برنامه از کار بیفتد یا Redis در دسترس نباشد، سفارش ثبت شده ولی پیامکی هرگز نمی‌رود. عکسش هم ممکن است: پیام در صف برود ولی تراکنش دیتابیس برگردد.

الگوی outbox این را حل می‌کند: پیام در همان تراکنشی که سفارش ذخیره می‌شود، در جدولی به نام outbox در همان دیتابیس نوشته می‌شود. یک فرایند جداگانه رکوردهای ارسال‌نشده outbox را می‌خواند، به صف می‌فرستد و علامت ارسال می‌زند.

BEGIN;
  INSERT INTO orders (...) VALUES (...) RETURNING id;      -- 981
  INSERT INTO outbox (topic, payload)
    VALUES ('order.created', '{"order_id": 981}');
COMMIT;

-- relay process, every few seconds
SELECT id, topic, payload FROM outbox
WHERE sent_at IS NULL
ORDER BY id
LIMIT 100
FOR UPDATE SKIP LOCKED;
-- publish each row to the queue, then: UPDATE outbox SET sent_at = now() WHERE id = ...

چون ثبت سفارش و پیام در یک تراکنش‌اند، یا هر دو ثبت می‌شوند یا هیچ‌کدام. ممکن است پیامی دو بار منتشر شود، که با idempotent بودن worker مشکلی ایجاد نمی‌کند.

کارهای زمان‌بندی‌شده بدون اجرای تکراری

بعضی کارها زمان‌بندی‌شده‌اند: گزارش شبانه، پاک کردن سبدهای رهاشده، استعلام پرداخت‌های بدون بازگشت از درگاه یا یادآوری تمدید اشتراک. چند نکته:

  • اگر برنامه روی چند سرور یا چند نمونه اجرا می‌شود، cron روی همه آن‌ها اجرا می‌شود. یا کار زمان‌بندی‌شده را فقط روی یک نمونه اجرا کنید یا با قفل (مثلاً advisory lock در PostgreSQL یا قفل Redis) جلوی اجرای هم‌زمان را بگیرید.
  • cron بهتر است کار را در صف بگذارد، نه اینکه خودش کار سنگین را انجام دهد؛ این‌طوری تلاش دوباره و پایش یکسان می‌ماند.
  • برای کارهای دوره‌ای «آخرین اجرای موفق» را ثبت کنید و اگر از حد مجاز قدیمی‌تر شد هشدار بگیرید. cronی که بی‌صدا متوقف شده، از رایج‌ترین خرابی‌های پنهان است.
  • در وردپرس، WP-Cron با بازدید اجرا می‌شود؛ برای کارهای مهم آن را غیرفعال و با cron واقعی سرور فراخوانی کنید.

کش: با قاعده انقضا و باطل‌سازی

کش در سطح برنامه، معمولاً با Redis، برای داده‌ای که زیاد خوانده و کم نوشته می‌شود مفید است: تنظیمات، فهرست دسته‌ها، نتیجه پاسخ‌های API بیرونی یا محاسبه‌های سنگین. رایج‌ترین الگو cache-aside است: اول از کش بخوان؛ اگر نبود، از منبع بخوان و در کش بگذار.

async function getCategoryTree() {
  const hit = await redis.get('catalog:tree:v3');
  if (hit) return JSON.parse(hit);
  const tree = await db.categories.buildTree();
  await redis.set('catalog:tree:v3', JSON.stringify(tree), 'EX', 600); // 10 min
  return tree;
}
// when an admin edits categories:
await redis.del('catalog:tree:v3');
  • برای هر کلید بدانید داده چقدر می‌تواند قدیمی باشد و TTL را با همان تنظیم کنید. موجودی انبار و قیمت لحظه‌ای با فهرست دسته‌ها فرق دارد.
  • هم انقضای زمانی بگذارید و هم هنگام تغییر داده کلید را پاک کنید؛ فقط یکی کافی نیست.
  • نسخه در نام کلید (v3) بعد از تغییر ساختار داده، کش ناسازگار قبلی را بی‌اثر می‌کند.
  • داده خاص هر کاربر را با شناسه کاربر در کلید کش کنید؛ کش اشتباهی که داده یک کاربر را به دیگری نشان دهد، نشت اطلاعات است.
  • برنامه باید بدون کش هم کار کند، فقط کندتر. اگر قطعی Redis کل سایت را از کار می‌اندازد، کش به وابستگی حیاتی تبدیل شده است.

جمع‌بندی

هر کاری که کند است یا به سرویس بیرونی وابسته است را به صف پیام و worker بسپارید تا کاربر منتظر نماند و قطعی یک سرویس سفارش را خراب نکند. کارها را idempotent بنویسید، تلاش دوباره را با فاصله افزایشی و سقف و صف خطا انجام دهید، با الگوی outbox جلوی گم شدن پیام را بگیرید، cron را با قفل اجرا کنید و کش را فقط با قاعده روشن انقضا و باطل‌سازی به کار ببرید. طول صف و سن قدیمی‌ترین کار را هم حتماً پایش کنید.

درس قبل طراحی دیتابیس و مدل‌سازی داده بود. درس بعد، مشاهده‌پذیری و پایداری وب‌اپ، نشان می‌دهد چطور بفهمید این صف‌ها و سرویس‌ها کی و چرا مشکل پیدا کرده‌اند. نقشه کامل دوره در راهنمای معماری نرم‌افزار است.

اگر وب‌اپ یا فروشگاهتان زیر بار کند می‌شود یا ارسال پیامک و اتصال به سرویس‌های بیرونی‌اش ناپایدار است، فرم درخواست پروژه را پر کنید.
